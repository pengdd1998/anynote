### ✅ ROOT CAUSE FOUND — DB password mismatch (NOT a code bug)
Server log on startup:
```
ERROR failed to ping database: failed to connect to `user=readpal database=anynote`:
  failed SASL auth: FATAL: password authentication failed for user "readpal" (SQLSTATE 28P01)
```
- The deploy is wired around a postgres superuser **`readpal`** (intentional — `infra/docker-compose.yml` `POSTGRES_USER: readpal`, `docker-compose.deploy.yml` `DATABASE_URL: postgres://readpal:${POSTGRES_PASSWORD:-changeme}@...`, `cd.yml` `psql -U readpal`).
- **Mismatch:** the password the app passes (`${POSTGRES_PASSWORD:-changeme}` from the deploy environment) ≠ the password persisted for `readpal` in the `postgres_data` volume. Postgres only honors `POSTGRES_PASSWORD` on **first** volume init; subsequent restarts keep the original password, so an env drift breaks auth.
- **Why CD showed green:** `cd.yml` runs migrations as `IMAGE_TAG=$TAG docker compose -f docker-compose.deploy.yml run --rm server /app/migrate up || true` — the `|| true` **swallows** the DB-auth/migration failure, so CD reports success; the server then starts and crashes on the DB ping.
- This is an **ops/secrets** issue, not a `main` code bug. The earlier "staleness / cfa5b91" line of investigation was a red herring — the register-500 was DB-auth failure all along.
- **Fix (server-side):** make the app's `POSTGRES_PASSWORD` match the volume's `readpal` password, e.g. reset it and pin via `.env`:
  ```bash
  docker exec infra-postgres psql -U readpal -c "ALTER USER readpal PASSWORD 'NEWPWD';"   # docker exec = trust auth, works despite network auth failing
  echo "POSTGRES_PASSWORD=NEWPWD" >> <deploy-dir>/.env
  cd <deploy-dir> && IMAGE_TAG=v2.7.5 docker compose -f docker-compose.deploy.yml run --rm --no-deps server /app/migrate up   # no || true — see real errors
  IMAGE_TAG=v2.7.5 docker compose -f docker-compose.deploy.yml up -d
  docker logs anynote-server --tail 30
  ```
- **Repo hardening (recommended, separate):** drop the `|| true` on the migrate step in `cd.yml` so migration/DB-auth failures fail the deploy loudly instead of masking as green.

## 2026-06-16 — P1 search bug FIXED + verified on device

Root-caused the "local note search returns no results" defect (3 layered bugs) and fixed all three; verified end-to-end on SM-N9600.

**Root cause:**
1. `notes_fts` was created as a *regular* table by Drift's `createAll()` (`NotesFts` is a plain `Table` in the `@DriftDatabase` tables list); the later `CREATE VIRTUAL TABLE IF NOT EXISTS ... fts5(...)` was a no-op → `MATCH` invalid on a regular table → empty results.
2. The FTS5 tokenize directive `unicode61 categories "L* N* Co"` was malformed → `parse error in tokenize directive`. Masked by #1 (virtual table never got created).
3. FTS5 restricts DELETE/UPDATE `WHERE` to rowid/MATCH; `_updateFts`'s `DELETE ... WHERE note_id=?` threw on a virtual table (broke note creation once #1 was fixed).

**Changes (frontend/):**
- `lib/core/database/app_database.dart`: `schemaVersion` 19 → 21; `onCreate` calls `_recreateFtsTable()` after `createAll()`; `onUpgrade` adds `from<20` and `from<21` steps calling `_recreateFtsTable()` to repair existing installs; tokenizer → plain `unicode61` (CJK still indexed — `Lo` ⊂ default `L*`).
- `lib/core/database/daos/notes_dao.dart` (`_updateFts`, `softDeleteNote`) + `lib/core/database/daos/note_properties_dao.dart`: DELETEs use `WHERE rowid IN (SELECT rowid FROM notes_fts WHERE note_id = ?)` (FTS5-safe; works on regular tables too).

**Verification:** clean rebuild + reinstall; login `qadev01`; created note "dragonfly" (persisted in list); search "dragonfly" returned it. No `SqliteException`/tokenize errors in logcat. Not yet committed — awaiting go-ahead.
